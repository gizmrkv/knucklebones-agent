# Deep Research スキル

OpenAI / Gemini / Perplexity / Anthropic の Deep Research 系製品で共通する実装パターン（計画分離・並列探索・文単位引用・努力スケーリング）を Claude Code 上で再現する。専用 RL モデルは使えないので、ハーネス側の工夫（プロンプト設計・ツール並列・サブエージェント・チェックポイント）で品質を出す。

## 使う / 使わないの判断

| 状況 | 使うか |
| --- | --- |
| 「○○について包括的に調べてレポート」 | 使う |
| 「比較表を作って」「賛否両論を整理」 | 使う |
| 「最新動向を Pros/Cons で」 | 使う |
| 「○○の定義を教えて」（1 検索で済む） | 使わない |
| コードベース内の探索 | 使わない（Explore agent / grep を使う） |
| 単一 URL の要約 | 使わない（WebFetch 直接） |

> **コスト注意:** subagent 並列構成は通常チャットの約 15× のトークンを消費する（Anthropic 報告）。価値の高い質問に絞る。light モード（subagent を spawn せずメインだけで完結）で足りるなら subagent を使わない。

## 6 フェーズの実行手順

### フェーズ 0: ワーキングディレクトリの確認と出力先の初期化

**目的:** 調査開始前に作業文脈を把握し、レポートの置き場所を確定・作成する。

1. `pwd` でカレントディレクトリを確認する
2. 出力ディレクトリを以下の命名規則で決定する（フェーズ 1 でテーマが確定してから実行）:

   ```
   docs/YYYYMMDD-<topic-slug>/
   ```

   - `YYYYMMDD`: 実行日（例: `20260513`）
   - `<topic-slug>`: トピックを英語 kebab-case で 3〜5 語に圧縮（例: `llm-evaluation-methods`）
   - ベースは `pwd` 直下の `docs/` ディレクトリ

   例: `docs/20260513-llm-evaluation-methods/`

3. `mkdir -p <dir>/findings` でディレクトリを作成する
4. 以降のすべての出力（`plan.md` / `findings/*.md` / `README.md`）をこのディレクトリ以下に書く

### フェーズ 1: 明確化（Clarification）

**必ず以下の 2 ステップを順に実施する。指示なく省略をしたり仮定を置いてはいけない。**

#### ステップ 1: 調査テーマの確定

- 呼び出しメッセージに調査テーマが含まれている場合 → そのまま使用する
- テーマが含まれていない場合 → 次の文言でテキスト入力を求め、返答を受け取るまで次のステップへ進まない:

  ```
  調査テーマを教えてください。
  ```

#### ステップ 2: AskUserQuestion ツールを呼び出す

テーマ確定後、**以下の AskUserQuestion を呼び出す。文言・選択肢・順序を変えない。**
どれを推奨するかは検索テーマに応じてその都度判断する。

```
AskUserQuestion(
  questions=[
    {
      header: "調査の深さ",
      question: "調査の深さを選んでください",
      multiSelect: false,
      options: [
        {label: "light",  description: "〜10 検索。素早い概要把握"},
        {label: "medium", description: "〜30 検索。バランスの取れた調査"},
        {label: "deep",   description: "30+ 検索。並列サブエージェントで徹底調査"}
      ]
    },
    {
      header: "成果物形式",
      question: "レポートの形式を選んでください",
      multiSelect: false,
      options: [
        {label: "構造化レポート", description: "README 形式、セクション・引用付き"},
        {label: "簡易メモ",     description: "箇条書きの要点のみ"},
        {label: "比較表",       description: "複数の選択肢・製品・手法を並べて比較"}
      ]
    },
    {
      header: "既存ファイル参照",
      question: "作業ディレクトリ内の既存ファイル・ディレクトリを参照してもよいですか？",
      multiSelect: false,
      options: [
        {label: "参照してよい", description: "重複調査の回避・関連情報の把握のために既存ファイル・ディレクトリを確認する"},
        {label: "参照しない",   description: "既存ファイル・ディレクトリには一切アクセスせず、新規に調査する"}
      ]
    }
  ]
)
```

「参照してよい」の場合、フェーズ 0 で既存ディレクトリや関連ファイルを確認し、重複調査や参考にできる過去の知見がないか把握してから進める。「参照しない」の場合、既存ファイル・ディレクトリの閲覧は行わず新規ディレクトリの作成のみ行う。

#### ステップ 1.5: テーマのスコープが曖昧な場合の追加確認（条件付き）

テーマに対象期間・対象読者・比較軸・地域などスコープを左右する要素が未指定で、それによって調査の広さ・深さが大きく変わりうる場合のみ、AskUserQuestion（ステップ2）の前かAskUserQuestion内の追加質問として、1〜2個の自由記述確認を挟んでよい（OpenAI Deep Research API が推奨する「明確化質問」パターンに準拠）。テーマが十分具体的なら省略する。

- 聞くべき例: 「最新動向」と言われたが対象期間が不明、「比較して」と言われたが比較対象の候補が不明、専門家向けか初学者向けかで深さが変わる、など
- 聞かない例: 出力の構造・深さを変えない些末な好み、ユーザーが既に言及している内容の重複確認

### フェーズ 2: 計画（Planning）

**目的:** 探索開始前にサブクエスチョンへ分解し、ユーザーがレビューできる形で提示する。

#### クエリ型分類（execution strategy）

メインクエスチョンを以下の 3 型に分類する。型は subagent 数と分担方針を決める軸で、`light/medium/deep` の予算軸とは直交する（併用する）。

| 型 | 特徴 | subagent 数の目安 | 分担方針 |
| --- | --- | --- | --- |
| Straightforward | 単一の事実・定義・統計を 1〜数ソースで埋められる | 0–1 | メインが直接 WebFetch、または 1 subagent |
| Depth-first | 1 トピックを多角的に深掘り（賛否・歴史・技術詳細） | 2–4 | 同一トピックを別観点で並列分担（賛成/反対、定量/定性、最新/歴史 等） |
| Breadth-first | 独立した複数サブトピックの並行調査（比較・landscape） | 3–10 | 各 subagent に独立サブトピックを 1 つずつ分担 |

#### 計画テンプレ

以下のテンプレで計画を出力する:

```markdown
## リサーチ計画

**メインクエスチョン:** <一文>

**クエリ型:** <Straightforward / Depth-first / Breadth-first>

**サブクエスチョン:**
1. [事実確認] <定義・基本事項>
2. [現状把握] <最新動向・主要プレイヤー>
3. [比較] <選択肢間の差異>
4. [反証] <批判・限界・失敗例>
5. [一次情報] <論文・公式仕様・統計原典>

**情報源の優先順位:**
- 一次: <論文 / 公式ドキュメント / 統計>
- 二次: <信頼できる解説記事>
- 除外: <SEO スパム / 古い情報 / 利益相反>

**深さ予算:** <light / medium / deep>
**subagent 数上限:** <N>（クエリ型から導出）
**推定時間:** <X 分>

レビューして OK なら開始する。
```

プランを作成したらユーザーに確認を取る(Y/n)

### フェーズ 3: 探索（Exploration）

**目的:** 並列ツール呼び出しと努力スケーリングで効率的に情報収集する。

#### 努力スケーリングの目安

| 深さ | サブクエリ数 | サブエージェント | 並列 WebFetch |
| --- | --- | --- | --- |
| light | 3–10 | 不要 | 〜3 並列 |
| medium | 10–30 | 必要に応じ 2–3 個 | 3–5 並列 |
| deep | 30+ | 3–5 個（独立トピック分担） | 5+ 並列 |

#### 探索の原則（Anthropic のマルチエージェント研究より）

- **Lead は synthesis 専任、検索は subagent:** メインエージェント（lead）は計画と統合だけを担い、subagent を使う場合は自身で WebFetch を打たない。役割混在は context 汚染と subagent との重複作業を生む
- **Start broad, then narrow:** 最初は広く landscape を取り、その後 specific に掘る。最初から狭いクエリに行かない
- **多角化:** 同義語・反対概念・関連分野からも検索（1 クエリで終わらせない）
- **反証の能動探索:** 「X は正しいか」だけでなく「X が間違っている根拠」も別クエリで投げる
- **具体例・事例の能動収集:** 抽象的な主張の裏付けとして、OK 例・NG 例・実際の事例（成功事例・失敗事例・ケーススタディ）を見つけ次第、積極的に検索・収集する。「〜すべき」「〜が有効」といった一般論だけで終わらせず、「具体的に誰が・いつ・どう行ったか」を別クエリで掘る。収集した実例は出典 URL とともに `findings/` に保存し、フェーズ 4 の「例示」セクションで使う
- **並列実行:** 独立した検索・取得は単一メッセージで複数 tool call にまとめる
- **deep モードではサブエージェント:** `Agent` ツール（subagent_type=general-purpose）に独立サブクエスチョンを分担させる。サブエージェント内で並列検索 → 200 語以下のサマリで返却してもらう
- **中間進捗の報告（deep モード）:** サブエージェント群が返るまで数分〜十数分かかるため、バッチが完了するたびに1文程度でユーザーに状況を伝える（例:「A社の調査が完了しました。残りB件を並列起動します」）。無言で長時間経過させない

#### サブエージェント分担のテンプレ（4 要素必須）

Anthropic の知見に基づき、subagent への指示は **objective / output format / tool guidance / task boundaries** の 4 要素を必ず含める。曖昧な指示は重複と空白を生む。

```
Agent({
  description: "<サブクエスチョン名>",
  subagent_type: "general-purpose",
  prompt: """
  # Objective
  <サブクエスチョン（一文）>

  # Output format
  - 発見1: <事実> [出典](URL)
  - 発見2: ...
  - 具体例・事例: <OK 例 / NG 例 / 実際のケース> [出典](URL)（見つかった分だけ列挙。無理に作らない）
  - 限界・未解決: ...
  （200 語以内、本文の詳細は findings/<subq>.md にこのエージェント自身が書き込む）

  # Tool guidance
  - 一次情報優先（論文 PDF / 公式 docs / 統計原典）
  - 多角クエリ 5–10 個、反証も別クエリで探す
  - 抽象的な主張だけで終わらせず、OK例・NG例・実例・事例を専用クエリで能動的に探す
  - 並列 WebFetch 推奨（独立 URL は単一メッセージでまとめて取得）

  # Task boundaries
  - クエリ数上限: <N>
  - スコープ外: <扱わないトピック>
  - 3 回連続で空振りなら諦めて「該当なし」と記録
  """
})
```

#### External memory（subagent 結果のオフロード）

deep モードでは subagent 返答をすべてメイン context に展開しない:

- subagent には 200 語以下の要約のみメインに返却させる
- 詳細な発見・引用は subagent 自身に `findings/<subq>.md` へ書き込ませる
- メインエージェントは要約と URL リストだけで synthesis を組み、必要に応じてファイル経由で詳細を参照

これでメイン context が 200K に達する前に subagent 数を増やせる。

#### 動的停止条件（gap analysis）

固定回数ループは「複雑クエリで早期打ち切り、簡単クエリで過剰検索」を招く。各ラウンド末尾で以下を自己評価する:

- 計画したサブクエスチョンのカバー率: 0.0–1.0
- 矛盾・未解決リストの件数
- 一次情報の欠落: あり / なし

**判定ルール:**

- カバー率 ≥ 0.8 かつ未解決 ≤ 1 件 → 停止してフェーズ 4 へ
- カバー率 < 0.8 → 不足箇所を埋める追加サブクエリを 1 ラウンド実行
- 同じ追加クエリで 2 ラウンド連続で改善なし → 停止して「未解決」セクションに記録（diminishing returns）

最大 3 ラウンドで強制停止。「3 回空振りで諦め」（負のシグナル）と「カバー率閾値で停止」（正のシグナル）を併用する。

#### ソース品質ヒューリスティクス

放っておくと SEO スパムを優先しがち。プロンプトで明示する:

- 一次情報（論文 PDF・公式 docs・統計原典）を二次情報より優先する
- 発行日を確認し、対象トピックの陳腐化速度に応じて古い情報を排除
- ドメイン信頼性（.gov / .edu / 公式 / 査読あり > 個人ブログ > Medium / Qiita 等）
- 利益相反（自社製品宣伝・スポンサー記事）に注意
- 数値・統計は必ず原典に遡る

### フェーズ 4: 統合（Synthesis）

**目的:** 主張を構造化レポートに落とす。**引用 `[^N]` の付与は本フェーズでは行わず、フェーズ 4.5 で別 turn で実施する**（生成中に引用を強制すると post-rationalization が混入するため。RAG 引用の最大 57% が事後正当化との報告）。

本フェーズでは引用が必要な箇所に `[要引用]` プレースホルダを残しておく。

#### 前提知識ゼロ読者向けの記述ルール（必須・常時適用）

調査レポートは日本語で出力する。デフォルト想定読者は「該当テーマについて前提知識を一切持たない読者」とする。論文・公式 docs にアクセスしたことがない読者を想定すること。

**読者の置き方（必須）:**
- 想定読者に「話しかける」つもりで書く。聴衆ペルソナ（読者を指定する）を採用し、話者ペルソナ（「あなたは専門家です」「あなたは〇〇の研究者です」型）は使わない。話者ペルソナは accuracy の悪化が実証されている

**専門用語・固有名詞:**
- 初出時に必ず「**○○** = △△する〜」型の 1 行定義を併記する
- 固有名詞（組織・人名・製品）には「業種・地域・代表的活動」のいずれか 1 つ以上を 1 行で添える
- ジャーゴンを多く含むトピックでは「TL;DR」の直下に「用語集（初出順）」セクションを設ける

**文体:**
- 1 文 60 字以内を目安にする
- 受動態より能動態を優先する
- 「非常に」「とても」「かなり」など効果の薄い副詞を控える
- 5 行以上の連続段落は箇条書きに分解する
- 各章・各セクションの冒頭で「この節で何が分かるか」を 1 文で宣言する

**事実精度の safeguards（過剰一般化対策）:**
- 数値には qualifier（対象母集団・期間・条件・国/地域）を必ず保持する。「75% が改善」だけで止めず「<どの集団>の 75% が<どの期間で>改善」と書く
- 「もしかすると」「おそらく」「〜と思われる」を使わない。事実か「未確認:」ラベル付きの推測かを明示する
- self-instruct として「正確に書け」「漏れなく書け」を**入れない**（generalization bias を増やすことが実証されている）
- 時制を勝手に普遍命題化しない（過去研究の結果を現在形の一般法則として書かない）

**例示:**
- 1 セクションに 1 つ以上の身近な具体例を入れる。フェーズ 3 で能動収集した OK 例・NG 例・実例・事例を優先的に使う
- ただし source に無い具体例を「事実」として書かない（elaborative hallucination を避ける。フェーズ 3 で見つからなかった場合は無理に作らず「具体例: 未確認」と明示する）

#### 出力テンプレート（ファイル保存版・最終形）

以下は最終形態。フェーズ 4 ではテンプレ中の `[^N]` を `[要引用]` で書き、フェーズ 4.5 で実引用に置き換える。

```markdown
# <タイトル>: <リサーチクエスチョン>

## TL;DR
- <1〜3 行の結論>

## 用語集（初出順、ジャーゴンを含むトピックの場合のみ）
- **<用語1>** = <1 行の平易な定義>
- **<用語2>** = <1 行の平易な定義>

## 主要な発見
- **<発見 1 のラベル>:** <事実> [^1]
- **<発見 2 のラベル>:** <事実> [^2]

## 詳細

### <論点 A>
- **観察:** <事実> [^3]
- **解釈:** <因果や背景の説明>
- **対立する見解:** <あれば> [^4]

### <論点 B>
...

## 矛盾・未解決
- <情報源間で食い違う点>
- <一次情報が見つからなかった点>

## 限界
- <調査範囲・期間・言語の制約>
- <推測と事実の境界>

## 引用
- [^1]: [タイトル](URL) — 該当箇所抜粋
- [^2]: [タイトル](URL) — 該当箇所抜粋
...

## メタ情報
- 調査日: YYYY-MM-DD
- 深さ: <light/medium/deep>
- 検索クエリ履歴: <主要なクエリ 5–10 個>
- 棄却した情報源: <信頼性が低かったもの>
```

#### 統合の原則

- **1 主張 = 1 つ以上の引用が必要だが、付与はフェーズ 4.5 で行う。** 本フェーズではプレースホルダ `[要引用]` を残す
- **推測と事実を視覚的に分離。** 推測には「推測:」「未確認:」のラベル
- **数値はラベルとセットで提示。** 「CTR: 1.23%（前比 +0.15pp、`[要引用]`）」
- **矛盾を平準化しない。** 情報源間で食い違うときは両方併記
- **長文段落を書かない。** 5 行以上の連続テキストは箇条書きに分解（CLAUDE.md ドキュメント規約）
- **比較表のセルも本文と同じ引用規律に従う。** 出典があれば `[要引用]`、なければ「記述限定的」「未確認」と明示する。1 つのセル内で「記述限定的」と書きながら別の具体的事実を無出典で追記しない（自己矛盾になる）

### フェーズ 4.5: 引用付与（Citation Pass）

**目的:** 本文生成と引用付与を分離し、post-rationalization を防ぐ。Anthropic の CitationAgent パターンに準拠。

**手順:**

1. フェーズ 4 のドラフト本文を読み、`[要引用]` プレースホルダの位置をすべて列挙する
2. `findings/*.md`（subagent 返答）に蓄積された URL リストと突合し、各主張に最も妥当な URL を最低 1 件紐付ける
3. 紐付けできない主張 → 「未確認」ラベルに格下げ、または削除
4. 脚注番号を本文中の初出順に振り直し、`[^1]`, `[^2]`, ... と欠番なく連番になっていることを確認してから「引用」セクションを生成する（源データ側の管理番号をそのまま引用番号に流用すると欠番が生じやすいので注意）

**spot check:** 紐付けた URL のうち最低 1 件は WebFetch で実在と内容一致を再確認する（hallucination 引用の検出）。優先順位は「%・件数などピンポイントに具体的な数値」「桁数の大きい統計」「他情報源と矛盾しうる固有名詞・バージョン表記」の順に高い。フェーズ 5 の指摘を待たず、ドラフト中で最も具体的な数値主張から先に検証する。

**禁則:** 本フェーズで「新規の主張」を追加しない。引用に合わせて本文を捏造することを防ぐため、本文の内容変更は最小限（プレースホルダ → 脚注番号への置換、未確認ラベルへの格下げのみ）に留める。

### フェーズ 5: 自己レビュー（独立検証）

**同一文脈での self-critique は degeneration-of-thought に陥る**（Chain-of-Verification）。最終レポートだけを別サブエージェントに渡し、ドラフト過程・findings の文脈なしで判定させる。

#### 検証サブエージェントのテンプレ

```
Agent({
  description: "Deep research 検証",
  subagent_type: "general-purpose",
  prompt: """
  # Objective
  以下のレポートを独立にレビューする。私（lead）のドラフト過程・findings ディレクトリは見せない。

  # Input
  <README.md 本文をここに貼り付け>

  # Output format
  - [ ] 引用なし主張: <該当箇所、なければ「なし」>
  - [ ] 主張と引用が一致しない箇所: <claim と URL の不一致>
  - [ ] 一次情報の欠落: <二次情報のみで構成されている論点>
  - [ ] 反証 / 対立見解の探索が薄い論点: <あれば>
  - [ ] 限界・未解決の明示が不十分な箇所: <あれば>
  - [ ] 専門用語・固有名詞で初出時に 1 行定義が併記されていない箇所: <該当箇所>
  - [ ] 数値の qualifier（対象母集団・期間・条件）が欠落している箇所: <該当箇所>
  - [ ] 過剰一般化（時制シフト、qualifier 落ち、断定的書き換え）の疑い: <該当箇所>
  - [ ] 受動態・効果の薄い副詞が過多で読みにくい箇所: <該当箇所>
  - [ ] 「もしかすると」「おそらく」等のぼかしを使っている箇所: <該当箇所>
  - [ ] 脚注番号に欠番・重複がないか（1 から連番になっているか）: <該当箇所>
  - [ ] spot check すべき URL: <最も hallucination 疑いが高い 1–2 件>

  # Tool guidance
  - 必要なら spot check 推奨 URL を 1–2 件 WebFetch で確認

  # Task boundaries
  - レポート内の記述だけから整合性を判断する（推測でなく検査）
  - 新たなリサーチは行わない
  """
})
```

検証サブエージェントの指摘に基づき、フェーズ 3 に戻って追加探索する（最大 1 回）。軽微な修正（引用差し替え、ラベル付け直し、脚注の振り直し）はフェーズ 4.5 に戻して対応する。

**修正後の再検証基準:** 指摘が2〜3件程度の軽微な修正なら、適用後に本文を通し読みして矛盾がないか確認すれば十分で、検証サブエージェントの再起動は不要。指摘が4件以上、または「主張と引用の不一致」「一次情報の欠落」など内容面の重大な指摘を含む場合は、修正適用後にフェーズ 5 をもう一度だけ実行して解消を確認する。

### フェーズ 5 完了後: コミット

すべてのフェーズが終わったら `docs/YYYYMMDD-<topic-slug>/` 以下のファイルをコミットする。

```bash
git add docs/YYYYMMDD-<topic-slug>/
git commit -m "research: <topic-slug> (<YYYY-MM-DD>)"
```

コミットメッセージの形式:

- プレフィックス: `research:`
- 本文: kebab-case のトピック名（フェーズ 0 で決定したスラッグ）
- 末尾: `(YYYY-MM-DD)` 形式の実行日

例: `research: llm-evaluation-methods (2026-05-13)`

## チェックポイント運用

deep モードでは長時間実行になるため、フェーズごとに中間状態をファイルに書き出す:

```text
docs/YYYYMMDD-<topic-slug>/
├── plan.md           # フェーズ 2 の計画
├── findings/         # フェーズ 3 のサブエージェント返答
│   ├── <subtopic-a>.md   # 例: openai.md, academic.md など、汎用的な subq1.md より
│   └── <subtopic-b>.md   # 内容が分かるトピック名にした方が後から追跡しやすい
└── README.md         # フェーズ 4 の最終出力
```

中断・再開可能にすることで、トークン枯渇や API 障害に耐える。

## 失敗モード（観測されたもの）

- **過度に specific なクエリで開始** → 全体像を取り逃す。明示的に "broad" → "narrow" を指示する
- **SEO スパム優先** → 一次情報優先のヒューリスティクスをプロンプトに毎回記載
- **存在しない情報源を延々探索** → 3 回連続で空振りしたら諦めて「該当する一次情報なし」と記録
- **サブエージェントの暴走** → 各サブエージェントの予算（クエリ数・トークン数）を上限指定
- **引用の偽造（hallucination）** → 引用 URL を最低 1 件 spot check（WebFetch で実在確認）
- **確証バイアス** → 反証クエリを必ず別タスクとして投げる
- **ジャーゴン残存・固有名詞素手出し** → Phase 4「前提知識ゼロ読者向けの記述ルール」を厳守。初出時の 1 行定義を Phase 5 検証でチェック
- **過剰一般化（generalization bias）** → 数値の qualifier 保持を Phase 4 ルールに明記。self-instruct で「正確に」を入れない（逆効果が実証されている）
- **summarization と simplification の混同** → 内容を削るのではなく言い回しを平易化する。情報を落としそうな場合は「未確認:」ラベルか脚注に退避させる
- **elaborative hallucination（読者支援の偽造）** → source に無い具体例・比喩を「事実」として書かない。「例えるなら」と明示する
- **比較表セルの自己矛盾** → 「記述限定的」と書きつつ隣で無出典の具体事実を追記してしまう。Phase 4「統合の原則」の表セル引用規律を適用し、Phase 5 検証でもチェックする
- **脚注番号の欠番** → 情報源側の管理番号をそのまま引用番号に流用すると欠番が生じる。Phase 4.5 で本文初出順に振り直し、連番になっているか確認してから確定する
