# Paper Summary スキル

Keshav(2007)の3パス法と LLM 論文読解のベストプラクティスを組み合わせた論文精読・要約スキル。  
単純な「要約して」よりも構造化された問いを使い、アイデアの平板化を防ぐ。

## 使う / 使わないの判断

| 状況 | 使うか |
| --- | --- |
| PDF パス / arXiv URL / 論文テキストを渡して精読したい | 使う |
| 複数論文の比較・横断分析 | 使わない（deep-research を使う） |
| 論文を探したい | 使わない（deep-research を使う） |

## 引数

```
/paper-summary <pdf-path | url | ->  [depth=quick|full]
```

- `<pdf-path>`: ローカルの PDF ファイルパス
- `<url>`: arXiv 等の論文 URL（HTML版 または PDF）
- `-`: 標準入力（次メッセージで論文テキストを貼り付け）
- `depth=quick`（デフォルト）: Pass 1 + Pass 2 のみ、10 分以内で読める要約
- `depth=full`: Pass 1〜3、批判的評価・再実装視点まで含む詳細分析

## 実行フェーズ

### フェーズ 0: 入力の取得と出力先の決定

1. 引数を解析してソース種別（PDF / URL / テキスト）を判定する
2. 論文タイトルと著者・年を先読みして `<paper-slug>` を決定する（例: `attention-is-all-you-need-2017`）
3. 出力ディレクトリを決定する:
   ```
   research/YYYYMMDD-<paper-slug>/
   ```
4. `mkdir -p research/YYYYMMDD-<paper-slug>/` でディレクトリを作成する
5. 以降の出力をこのディレクトリに書く

**ソース別の取得方法:**
- PDF パス → `Read` ツールで読み込む
- arXiv URL → `/abs/` は `/html/` に変換してから `WebFetch`（LaTeX ソースが HTML 化されており数式精度が高い）
- その他 URL → `WebFetch` で直接取得
- `-`（テキスト貼り付け） → ユーザーの次メッセージを待つ

### フェーズ 1: Pass 1（全体把握、5〜10 分相当）

**目的:** 精読する価値があるかを判定し、論文の骨格を把握する。

以下の順序で読む（本文は読まない）:
1. タイトル・著者・年・掲載誌
2. アブストラクト
3. 序論（最初の段落と最後の段落）
4. セクション見出しの一覧
5. 結論（最初と最後の段落）
6. 図・表のキャプションのみ走査

読み終えたら **5C 評価** を出力する:

```markdown
## Pass 1: 5C 評価

- **Category（種別）:** 実験論文 / 理論論文 / サーベイ / システム論文 / ...
- **Context（背景）:** どの先行研究の文脈に位置するか
- **Correctness（妥当性）:** 仮定は妥当か（初見判断）
- **Contributions（貢献）:** 主張する新規性は何か
- **Clarity（明瞭さ）:** 読みやすいか

**精読判定:** depth=quick なら Pass 2 へ / 読む価値なし → ここで終了
```

### フェーズ 2: Pass 2（主要内容の把握）

**目的:** 論文の核心証拠と手法を把握する。本文の詳細（証明等）はスキップしてよい。

#### 2-A: 図表の先読み（**必ず自分の目で確認を促す**）

> **重要:** LLM は 2026 年ベンチマークで図・グラフの解釈が構造的に不十分と評価されている。色依存の可視化・精確な数値読み取りで一貫した失敗が確認済み。図表は必ずユーザー自身が原文 PDF で確認すること。

以下を読む:
- 全図のキャプションと図の構造（軸・凡例・傾向）を言語で記述する
- 全表の列名と代表値を記録する
- 「この論文の核心的証拠は図 N / 表 N にある」と明示する

#### 2-B: 構造化精読プロンプト

以下のフォーマットで論文を分析する（Pass 2 段階での出力）:

```markdown
## Pass 2: 構造化要約

### リサーチクエスチョン
<著者が答えようとしている問い（1〜2文）>

### 手法
<何をしたか：データ / モデル / 実験設計の骨格>

### 主要な発見
- <発見1>（根拠: 図N / 表N / セクションN）
- <発見2>（根拠: ...）

### 貢献（先行研究との差分）
<先行研究と比較した新規性>

### 限界（著者自身が認めているもの）
- <限界1>
- <限界2>

### 図表ハイライト
- **図 N:** <何を示しているか、読み取れること>
- **表 N:** <...>

⚠️ 図表の精確な数値・色分け・視覚的パターンは必ず原文 PDF で確認すること。
```

### フェーズ 3: Pass 3（深い理解）— `depth=full` のみ

**目的:** 著者の仮定を毎文ごとに検証し「仮想的に再実装」する視点で読む。

以下のプロンプトで批判的評価を行う:

```markdown
## Pass 3: 批判的評価

### 強み
- <方法論的な強み>
- <実験設計の強み>

### 弱み・疑問
- <仮定が成り立たない可能性>
- <実験で検証されていない主張>
- <比較ベースラインの選択に疑問>

### 暗黙の前提
- <明示されていないが論文が依存している前提>

### 再現性
- コード公開: あり / なし / 部分的
- 再現に必要な情報の充足度: 十分 / 不十分（何が足りないか）

### 自分の研究・仕事への示唆
- <応用できる知見>
- <追試・拡張の余地>
```

### フェーズ 4: レポートの生成

すべてのパスの結果を統合してレポートファイルを生成する。

#### 出力テンプレート

```markdown
# <論文タイトル>

**著者:** <著者名>  
**掲載:** <会議/ジャーナル名、年>  
**URL:** <論文URL>  
**要約日:** YYYY-MM-DD  
**精読深度:** quick / full  

---

## TL;DR

<1〜3 行の結論。「この論文は何を達成したか」を一言で>

---

## 5C 評価（Pass 1）

- **Category:** ...
- **Context:** ...
- **Correctness:** ...
- **Contributions:** ...
- **Clarity:** ...

---

## 構造化要約（Pass 2）

### リサーチクエスチョン
<一文>

### 手法
<骨格>

### 主要な発見
- <発見1> [^1]
- <発見2> [^2]

### 貢献
<差分>

### 限界
- <限界1>

### 図表ハイライト
- **図 N:** <説明>

⚠️ 図表の精確な解釈は原文 PDF で確認すること。

---

## 批判的評価（Pass 3）— full のみ

### 強み / 弱み / 暗黙の前提 / 再現性 / 示唆
<上記フェーズ 3 の内容>

---

## 引用

[^1]: <論文内の該当セクション / 表 / 図>
[^2]: ...

---

## メタ情報

- 要約日: YYYY-MM-DD
- 精読深度: quick / full
- ソース: <取得元 URL またはファイルパス>
- ⚠️ 引用幻覚注意: LLM 生成の引用は必ず原文で確認すること（GPT-4 クラスで DOI 正確率 16〜20%）
```

ファイルを `research/YYYYMMDD-<paper-slug>/README.md` に保存する。

### フェーズ 5: コミット

```bash
git add research/YYYYMMDD-<paper-slug>/
git commit -m "research: <paper-slug> (<YYYY-MM-DD>)"
```

## 落とし穴と対策

| 問題 | 対策 |
| --- | --- |
| 図表の読み落とし | フェーズ 2-A で必ず「原文 PDF で確認」を明示 |
| 引用幻覚 | 引用は論文内の「セクション名 / 表 N / 図 N」に限定し、外部 URL を捏造しない |
| アイデアの平板化 | 「Summarize」ではなく構造化フォーマットを強制 |
| 受動的要約 | Pass 3 の「仮想的再実装」視点で能動的問いを立てる |
| LLM の過大評価バイアス | 批判的評価プロンプトに「not just a positive summary」を明示 |

---

## 注意事項

- **引用生成の禁則:** 外部 URL や DOI を LLM が生成することを禁ずる。引用は論文内の箇所（セクション・図・表）への参照のみ。外部引用が必要なら `[要確認: <タイトル>]` とプレースホルダを置く。
- **図表:** LLM は色依存の可視化・精確な数値読み取りが不十分。図表の解釈は必ずユーザーが原文 PDF で確認する。
- **深い理解の損失防止:** レポートを読んだ後に「自分の言葉で 3 行要約を書く」ことを推奨する（LLM への認知オフロードが深い符号化を損なうため）。
